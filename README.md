# Учебный обмен по UDP

Клиент и сервер на C++17 выполняют `INIT → INIT_ACK → CONFIRM → CONFIRM_ACK` и выводят `ok exchange=<id>` после успешной проверки. Сокетами служат POSIX UDP-сокеты; внешние фреймворки не используются.

## Сборка и запуск

```sh
cmake -S . -B build
cmake --build build
```

Сборка выполняется с `-Wall -Wextra -Werror`. В первом терминале запустите сервер; `0` означает выбор свободного порта ОС:

```sh
./build/server 127.0.0.1 0
# listening 127.0.0.1:54321
# ok exchange=42
```

Во втором терминале передайте клиенту **порт, напечатанный сервером**:

```sh
./build/client 127.0.0.1 54321
# ok exchange=42
```

Номер порта и `exchange_id` в примере условные. Можно указать серверу конкретный локальный IPv4 и порт вместо `127.0.0.1 0`; адрес `0.0.0.0` означает прослушивание всех интерфейсов и не является адресом для запуска клиента. При ошибке `bind` сервер завершается с кодом 1.

## Пакеты и состояния

Одна UDP-датаграмма — одно сообщение: 12 байт заголовка и полезная нагрузка до 2048 байт. Заголовок: `magic` (4 байта, `0x4B455931`), `version` (1 байт, `1`), `type` (1 байт: `INIT=1`, `INIT_ACK=2`, `CONFIRM=3`, `CONFIRM_ACK=4`), `flags` (1 байт, `0`), `reserved` (1 байт, `0`), `exchange_id` (4 байта). Целые записываются старшим байтом первым (network order). Длина пакета определяется длиной датаграммы.

`INIT` содержит 32 байта `client_random`, `INIT_ACK` — 32 байта `server_random` и 32 байта `nonce`, оба подтверждения — 32 байта HMAC. Источник случайных байтов и ID — `std::random_device`.

Сервер без таймаута ждёт первый корректный `INIT` и держит только одну активную попытку. Затем до 5 секунд ждёт `CONFIRM` с теми же `exchange_id` и IP:портом отправителя. Неправильный HMAC, чужие и некорректные пакеты не продлевают попытку; один ID повторно не начинает новую попытку. Клиент отправляет каждое сообщение один раз и ждёт ответы от указанного IP:порта с тем же ID до общего дедлайна в 5 секунд. При неверных полях или длине пакет отклоняется, причина пишется в `stderr`, состояние не меняется. Ответ сервер отправляет отправителю принятой датаграммы.

## Расчёт секрета и HMAC

Порядок входных байтов **не зависит от расположения полей в C++-структуре**:

```text
secret = SHA256(client_random || server_random || nonce || exchange_id)
tag    = HMAC-SHA256(secret, type || exchange_id || client_random || server_random || nonce)
```

Здесь `type` — один байт (`CONFIRM` или `CONFIRM_ACK`), а `exchange_id` — четыре байта в network order. `CryptoContext` подаёт поля в SHA-256 последовательно, не собирая их копию в общий буфер. Для HMAC 32-байтный ключ дополняется до 64 байт, XOR с `ipad=0x36` и `opad=0x5c`, затем считается `SHA256(opad || SHA256(ipad || сообщение))`. Контексты SHA-256 и промежуточные блоки HMAC затираются после расчёта.

В `third_party/sha-256.c` и `third_party/sha-256.h` находятся **неизменённые** файлы [amosnier/sha-2](https://github.com/amosnier/sha-2): [исходник](https://github.com/amosnier/sha-2/blob/master/sha-256.c), [заголовок](https://github.com/amosnier/sha-2/blob/master/sha-256.h), [лицензия Unlicense/0BSD](https://github.com/amosnier/sha-2/blob/master/LICENSE.md). Взятый код хранит восемь 32-битных слов состояния, обрабатывает данные блоками по 64 байта, дополняет последний блок и выдаёт 32-байтный хеш. `sha_256_init(ctx, hash)` принимает контекст и выходной буфер, `sha_256_write(ctx, data, size)` добавляет байты, `sha_256_close(ctx)` завершает расчёт и возвращает указатель на выходной буфер. HMAC написан в `include/cryptography.hpp` поверх этих функций.

После завершения попытки деструктор `CryptoContext` затирает `secret` и случайные байты. `src/secure_zero.c` — отдельная реализация на чистом C: записи через `volatile unsigned char*` не удаляются компилятором как неиспользуемые. Тег HMAC сравнивается без раннего выхода при несовпадении байтов.
